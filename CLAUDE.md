## Next.js 16 — Critical Conventions

> These differ from older Next.js versions. Follow them exactly.

### `params` and `searchParams` are Promises

```tsx
// ✅ Correct — must await
export default async function Page({ params }: { params: Promise<{ slug: string }> }) {
  const { slug } = await params
}

// ❌ Wrong — old pattern, will break
export default function Page({ params }: { params: { slug: string } }) {
  const { slug } = params
}
```

### Use `PageProps` / `LayoutProps` helpers (no import needed)

```tsx
// Typed automatically — generated by next dev / next build
export default async function Page(props: PageProps<'/blog/[slug]'>) {
  const { slug } = await props.params
}

export default function Layout(props: LayoutProps<'/dashboard'>) {
  return <section>{props.children}</section>
}
```

### Server vs Client Components

- All `page.tsx` and `layout.tsx` files are **Server Components by default**
- Add `'use client'` only to files that need interactivity (state, effects, browser APIs)
- Keep `'use client'` boundaries as deep/narrow as possible to minimise bundle size
- React context providers must be Client Components; wrap `children` only, not the full `<html>`

### Routing conventions

| Pattern | Use |
|---|---|
| `app/foo/page.tsx` | Static route `/foo` |
| `app/foo/[slug]/page.tsx` | Dynamic segment `/foo/:slug` |
| `app/foo/[...slug]/page.tsx` | Catch-all |
| `app/foo/layout.tsx` | Nested layout for `/foo` and children |
| `app/api/route.ts` | Route Handler (replaces `pages/api`) |

### Data fetching

- Fetch in Server Components directly (no `useEffect`)
- Pass data down to Client Components as serialisable props
- `searchParams` prop opts a page into **dynamic rendering** — avoid if not needed

## CSS Conventions (Tailwind v4)

> This project uses **Tailwind CSS v4** — the setup differs significantly from v3. Read carefully.

### How v4 works in this project

- `globals.css` starts with `@import 'tailwindcss'` — this single line enables all Tailwind utilities
- **No `tailwind.config.js`** — configuration is done in CSS via `@theme` blocks
- Design tokens are defined in `globals.css` using `@theme` and become available as Tailwind utility classes
- PostCSS handles everything via `postcss.config.mjs` with `@tailwindcss/postcss`

### Adding custom tokens

```css
/* In globals.css */
@theme {
  --color-brand: #6366f1;       /* → use as bg-brand, text-brand, border-brand */
  --font-sans: 'Inter', sans-serif; /* → use as font-sans */
  --spacing-18: 4.5rem;         /* → use as p-18, m-18, etc. */
}
```

### Light/dark mode

Tokens are re-declared inside a `@media (prefers-color-scheme: dark)` `@theme` block — Tailwind picks them up automatically.

### Current tokens

| Token | Light | Dark |
|---|---|---|
| `--color-background` | `#ffffff` | `#0a0a0a` |
| `--color-foreground` | `#171717` | `#ededed` |

Use as: `bg-background`, `text-foreground`

### ❌ Patterns to avoid

```js
// Don't create tailwind.config.js — not used in v4
// Don't use @apply with v3-only syntax
// Don't use the old content: [] scan config
```

## Environment Variables

- Only vars prefixed `NEXT_PUBLIC_` are included in the client bundle
- All other `process.env.*` vars are server-only and replaced with `""` on the client
